# 应用论文

应用论文的中心不是证明“EC 很强大”，而是证明：在明确的领域约束、数据和评价标准下，所建模的问题值得优化，且所选 EC 方法是合适且有证据的。

## 1. 应用论文的证据链

1. 真实任务和利益相关者是什么。
2. 决策变量、目标、约束和不确定性如何从领域问题映射而来。
3. 为什么精确方法、传统工程方法或领域启发式不足。
4. EC 的哪种特性适合该问题：黑箱、多目标、组合结构、并行、可处理非解析模型等。
5. 结果对领域意味着什么，而不只是 benchmark 分数。

## 2. Introduction

推荐顺序：

1. 领域问题和实际后果。
2. 领域现有做法及其约束。
3. 优化建模的困难：非解析评价、仿真昂贵、动态事件、多利益相关者、硬约束等。
4. 已有计算方法的缺口。
5. 本文应用建模和算法贡献。
6. 实际验证证据。

不要把应用背景写成宣传性段落；每个背景陈述最终都应连接到建模或实验。

## 3. 问题建模

必须清楚说明：

- 决策变量和可行编码；
- 目标及其单位/方向；
- 硬约束、软约束和违约处理；
- 数据来源、时间范围和代表性；
- 仿真器或评价器的准确性；
- 领域专家的偏好或决策规则；
- 模型简化及其后果。

如果问题是组合优化，说明编码是否能保证可行性；若不能，修复/惩罚策略是什么。

## 4. 基线选择

应用论文至少考虑：

- 领域当前实践或人工规则；
- 简单但强的启发式/精确方法（在规模允许时）；
- 相关 EC 基线；
- 本文算法的简化版本。

只与随机搜索比较通常不足以支持实际价值。

## 5. 实验与结果

除优化指标外，报告领域可解释结果：

- 成本、时间、风险、资源利用率、覆盖率、准确率等；
- 可行性率和约束违反；
- 对关键参数和不确定因素的敏感性；
- 实际运行环境和每次评价成本；
- 解是否可解释、可部署、可被领域专家接受。

如果有真实案例，明确案例是否只是 demonstration，还是独立验证。

## 6. 结论

应用结论应区分：

- 算法在测试实例上的表现；
- 对当前应用案例的价值；
- 能否推广到其他机构、数据、设备或市场；
- 部署前仍需解决的数据、监管、安全或工程问题。

避免把单个案例写成行业普遍结论。

## 7. 常见失败

- 应用背景很长，优化模型很弱。
- 没有领域基线。
- 约束处理不清楚。
- 只报告目标值，不报告实际意义。
- 用合成 benchmark 代替真实数据，却声称解决真实问题。
- 忽略伦理、安全、隐私或监管限制（当领域相关时）。
